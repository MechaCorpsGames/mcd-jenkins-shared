# The Steam signal truncates its protocol extraction to one line

Date: 2026-08-26

Status: Accepted

## Context

`Locate Client Artifacts` in `mcdSteamUploadPipeline.groovy` reads the protocol
the client build speaks out of the source build's `manifest.json`:

```
grep -oP '"protocolVersion"\s*:\s*\K[0-9]+' ${manifestPath} || true
```

`grep -oP` prints one line PER MATCH. The value is then interpolated **unquoted**
into the signal document written by `Publish Steam Signal`:

```
"protocolVersion": ${env.CLIENT_PROTOCOL_VERSION},
```

A manifest carrying the key twice therefore yields `"54\n54"`. Groovy's `.trim()`
strips surrounding whitespace but not an interior newline, so the value clears the
stage's non-empty guard and the heredoc emits:

```
    "protocolVersion": 54
54,
```

Confirmed by running the real extraction and the real heredoc against a two-key
manifest: `json.loads` fails with `Expecting ',' delimiter`.

The consequence is quiet rather than loud. `Publish Steam Signal` only reports the
failure it was built to report, a non-zero exit from the write, and the write
succeeds here. The build stays green, the file lands, and the proxy keeps relaying
the PREVIOUS signal because the new one will not parse. Players are told about an
older build than the one on Steam, and nothing anywhere goes red.

Today's manifest has exactly one `protocolVersion` key, so this is a guard on a
shape rather than a fix for a live outage. It is worth holding because the cost is
asymmetric and the trigger is remote: `manifest.json` is generated by a DIFFERENT
pipeline (`mcdClientPipeline`'s `Generate Compatibility Manifest`), so a field
added there can break this reader with no change to this file and no failing build
pointing at it.

Found while verifying mc-vt37, which named it as a known nit.

## Decision

Pipe the extraction through `head -1`.

`head -1` rather than `grep -m1`: `-m1` stops after the first matching LINE, and
`-o` prints every match ON that line, so a minified single-line manifest would
still emit two values. `head -1` truncates the OUTPUT, which is the thing being
constrained, and is already the idiom in this file (`find ... | head -1` locates
the manifest a few lines above).

The `|| true` tolerance is unchanged. The pipeline's exit status becomes `head`'s,
and `head` exits 0 on empty input, so a manifest predating
`Generate Compatibility Manifest` still yields an empty value and the signal stage
still declines to write a signal it cannot fill in.

**`clientVersion` is deliberately left alone.** It has the same multi-match shape
and is also interpolated into the signal JSON, but unlike `protocolVersion` it
carries no `|| true`: today a missing `clientVersion` fails the sh step and the
build. Adding a pipe there would move the exit status to `head` and silently
convert a build-failing guard into an empty string, which is a worse trade than
the theoretical duplicate-key it would fix. Closing it properly means keeping the
missing-value guard explicit, and that is a separate change with its own decision
to make.

## Consequences

* A duplicated `protocolVersion` key now yields a parseable signal instead of a
  corrupt one.
* Two regression tests in `test/unit/test_mcd_steam_signal_stage.py` execute the
  real extraction and the real heredoc against a two-key manifest and assert the
  emitted document parses. Both fail with this change reverted.
* `clientVersion` keeps an open, documented instance of the same shape. It cannot
  corrupt the signal without a duplicate key in the manifest, and a duplicate key
  is exactly what nothing currently prevents.
